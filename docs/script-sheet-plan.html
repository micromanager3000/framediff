FRAMEDIFFREVIEWED IMPLEMENTATION PLAN · 2026-07-30

The script comp as a sheet

Turn kind="script" compositions from a fixed 16:9 canvas into a full-height, vertically scrollable sheet that owns the studio's middle area — five columns per scene, editable timing that ripples through every later row, reorderable rows, and a per-row source slot that points at either a comp or a media file.

↗ The prototypeprototypes/script · interaction reference ▶ Run it locallylaunch config script-lab · port 4181 ☰ Prototype READMEwhat each column and control does
IMPLEMENTED V1

This plan was checked against main@6f29707 before implementation. The shipped slice includes the full-height sheet, atomic ripple/reorder/insert/delete, addressable prose, comp and media source slots, and a preview tab that mounts the active row source with script overlays. The review replaced the proposed multi-placement session call with one explicit editPlan() runtime transaction: placement edits alone cannot move HTML elements or remove stale comp/media attributes.

01 What the prototype settles

The prototype is a standalone static page with an in-memory model — none of it touches the engine. Its value is that it answers the design questions, so implementation can argue about mechanism instead of layout.

DecisionWhat the prototype establishes
ShapeA document, not a canvas. Fills the middle area, scrolls vertically, free-form header on top, sticky column labels.
Five columnsDerived TIME · editable DURATION · NARRATION / DIALOG · VISUAL / SFX · SOURCE.
Timing truthDuration is the only timing input. Editing one ripples every later start; running time follows. Time is never edited directly.
Source slotA row points at either a comp or a media file. Both first-class, swappable as the scene firms up.
Row handlingReorder by drag or keyboard, delete with undo. Reordering re-derives timing exactly like a retime.
PreviewSecond tab: narration as captions, visual + SFX as a slate, over the row's source.
No type chipsNarration and dialog share a column with no VO/DIALOG label — the words carry it. SFX sits with the picture, not the spoken line.

02 The architectural fork

There are two established ways to own a surface in this studio, and they lead to very different amounts of work. This is the decision the whole plan hangs on.

A · A Svelte pane RECOMMENDED

Follows GenerativeWorkbench.svelte.

StudioShell.svelte:472 already swaps the entire centre pane on kind: {#if $store.current?.kind === "generate"} renders GenerativeWorkbench instead of PreviewHost, under a grid class .workspace.generate-workspace whose rows are 34px minmax(0,1fr) — a full-height single surface. A ScriptSheet.svelte mirrors that exactly.

  • Never enters the runtime's fit-scale path, so the 16:9 letterbox problem simply does not arise.
  • Source stays ordinary .html, so placements remain editable and the timeline keeps working.
  • Reuses editPlacements, editElementText, MediaPanel, assetDrag.ts.
  • The sheet is a studio view, so it is not visible outside the studio (a rendered script comp still letterboxes).

B · A composition-owned surface

Follows defineMoodboardComposition.

compositions/moodboard.ts emits a composition whose root carries data-fd-interactive, owns all its own pointer UX, and persists back through writeSource. The studio overlay stands aside via studio.css:1267.

  • The sheet travels with the composition, not the studio.
  • Blocked by the letterbox. studio-runtime/runtime.ts:4232 scales every stage by min(bounds.w/comp.w, bounds.h/comp.h). A filling, scrolling sheet cannot escape an outer transform: scale(), so this route must first change a hot path shared by every comp.
  • Generated comps declare sourceFormat: "generated" and their placements go read-only — timeline retiming of a script would stop working.
  • Sheet UX would be authored as generated HTML strings rather than components.
WHY A

Option B was the intuitive read — the prototype looks like a document, and moodboard is the document precedent. But moodboard is a card canvas with no temporal axis, while a script is a timed document whose rows are real clips. Keeping the source as plain HTML means parsePlanRows, planDrift, generateEditSkeleton, the timeline, and the Inspector all keep working on it unchanged, and the sheet becomes one more editor over the same data rather than a parallel one. It is also strictly less risky: no change to the shared render path.

03 The row contract

Rows are already clips. What they lack is addressable prose: in examples/previz-to-gen/src/compositions/Script.html the shot name, VO and beat text are plain <div> / <p> with no data-fd-id, and docs/STUDIO-EDITING-CONTRACTS.md requires a unique id for anything source-edited. So the port is mostly handing ids to text that already exists, plus splitting SFX out of the VO line. 

<!-- one row, after the port -->
<section class="row" data-fd-clip data-fd-id="scene-approach"
         data-fd-from="0" data-fd-duration="240"          <-- frames; from is derived by the sheet
         data-fd-prop-cast="cast-boat cast-lamp"
         data-fd-prop-location="loc-harbor-mouth"
         data-fd-prop-status="generated">              <-- PLANNING_STATUSES

  <h3 data-fd-id="scene-approach-title">Open-water approach</h3>
  <p  data-fd-id="scene-approach-nar">“Any light will do…”</p>      NARRATION / DIALOG
  <p  data-fd-id="scene-approach-vis">Low over the swell…</p>     VISUAL
  <p  data-fd-id="scene-approach-sfx">swell, a bell buoy</p>       SFX

  <!-- the source slot: a nested comp… -->
  <div data-fd-clip data-fd-id="scene-approach-src" data-fd-type="nested"
       data-fd-comp="harborShot" data-fd-trim-start="0"></div>
  <!-- …or a media file, the same slot with different attributes -->
  <img data-fd-id="scene-approach-src" data-fd-type="image"
       data-fd-src="asset://…" alt="">
WHAT THIS BUYS

parsePlanRows already skips clips nested inside a row, so the source slot never gets mistaken for a row. swapNestedComp already repoints data-fd-comp and advances data-fd-prop-status. The comp-vs-media switch is one attribute change on one element. No new file format, no second source of truth.

04 What has to be built

Three capabilities the codebase does not have yet. Everything else in the feature is assembly.

Ripple retiming

Ripple arithmetic lives in the pure retimePlanRows() transform. It rewrites the edited duration, every derived row start, each marked source slot's mirrored timing, and the composition duration in one source value. STUDIO-EDITING-CONTRACTS.md requires one gesture to be one transaction, so the runtime commits that value once.

Review finding: a multi-placement call is insufficient for the feature as a whole. Reorder, insert/delete, and comp↔media switching also change source structure. The correct boundary is CompositionRuntimePort.editPlan(request), with StudioSession.editPlan() providing editing state and notices. The arithmetic stays in planning.ts and is testable without a browser.

Row reordering

Rows render in source order under documentFlow (packages/framediff/src/runtime.ts:824), so a reorder must physically move the element and rewrite the from attributes of everything after it. insertNestedHtmlComposition can only append before the root's closing tag (:459) and cannot target a position, so this needs a new moveHtmlElement() / moveHtmlElementAfter() preserve the exact source fragment, and movePlanRow() follows with the same ripple pass. “Move to end” means after the last plan row, not after unrelated footer or script elements.

Plan-row verbs

planning.ts is pure string-in / string-out over HTML and has no notion of insert, move, or delete. It needs insertPlanRow, movePlanRow, deletePlanRow and a pure retimePlanRows, sitting beside the verbs that already exist.

08 V1 decisions from review

  1. Sheet owns the script workspace. The generic timeline and transport are not rendered inside the dedicated script branch. Preview navigation lives in the sheet. The authoring contract remains unchanged for API consumers and fallback surfaces.
  2. Status is not kind. The source picker shows composition kind; production maturity remains data-fd-prop-status from PLANNING_STATUSES. V1 does not invent a second ladder.
  3. Header notes live in HTML. An addressable element marked data-fd-script-field="summary" keeps prose and row timing on one source path. The existing JSON-bound title remains supported.
  4. Rendering is unchanged. Exporting a script composition still renders its authored canvas. The sheet is an authoring surface, not a new render mode.
  5. Preview is a reading aid. It mounts the row source and overlays script fields; it does not create or mutate the master edit.

09 Out of scope

  • Changing the runtime's fit-scale path — option A avoids needing it.
  • Existing planning.ts verb semantics; only additions.
  • Cast / locations / storyboard surfaces. They may want the same treatment later; their UX is separate work.
  • Deduplicating the three CompositionKind declarations.
  • Creating a new source composition inline from a row, automatic “fit scene to media,” and a Studio button for generateEditSkeleton. These cross project-operation and workflow boundaries and are follow-up features, not hidden requirements of the sheet editor.
  • Retiring left-edge accent rules elsewhere in studio.css (.composition-row.active, .asset-row.selected, .ms-tnode.active, .agent-check-panel li, .guide-step-detail) — a separate cleanup against the new convention.
