FrameDiff architecture · definition contract v2

One comp model.
Adapters, not species.

A composition is always the same project primitive. Its version defines compatibility, its type selects package-owned machinery, and its kind describes what the creator is making. Projects keep creative source and data; FrameDiff keeps the runtime and Studio UX.

LATEST-ONLY V2JSON BY DEFAULTPACKAGE-OWNED UXPROJECT-PINNED RELEASES

The policy

Version the boundary now; do not support old boundaries yet. A video project pins one FrameDiff revision. Updating that dependency deliberately adopts the current definition contract, runtime adapters, validation, and Studio UX. Version 2 rejects stale definitions with an actionable error. If backwards compatibility becomes valuable, migrations are added in one place—defineCompositionRegistry—without changing project registry shape.

Ownership

UX updates flow from the dependency

FrameDiff owns

Definition schema, constructors, registry validation, runtime adapters, kind defaults, compatible creation starters, Studio panels, runtime behavior, and eventual migrations.

The project owns

Stable registry keys, creative HTML/TypeScript, documents, schemas, timelines, recipes, assets, project-only tools, and the pinned FrameDiff revision.

The lockfile decides

Changing the pin is the upgrade event. No FrameDiff UI is copied into Jimmy Monster or an example, so the new package revision becomes the new UX automatically.

Project seam

One registry call is the upgrade gate

import { defineCompositionRegistry } from "framediff"; export const COMPOSITIONS = defineCompositionRegistry({ main: mainComp, previzCounter: previzCounterComp, shotCounter, jimmyRef: jimmyRefComp, });

Today · strict latest-only

Every entry must have the current definition version. Empty keys and duplicate composition IDs fail immediately. Runtime registry replacement validates again during HMR.

Later · optional compatibility

The same function can accept a union of old definitions, run pure ordered migrations, return only the current registry, and report which project sources should be rewritten.

Creation UX

Intent first, implementation second

The add flow never puts Edit, 3D, Generate, and Moodboard in one overloaded menu. It asks what the creator is making, then exposes only implementations that can produce that kind.

Daily workflows

Adding and updating comps

Add a comp

  1. Choose semantic intent (kind).
  2. Choose one compatible implementation (starter); the starter selects the runtime type.
  3. Author the generated source/data behind one stable registry key.
  4. Let typed compatibility plus runtime validation prove the current contract.

Update comp content

  1. Edit the project-owned source, document, timeline, recipe, or assets.
  2. Keep stable IDs and declared dependency paths.
  3. Run the project check/build; no type fork or copied UX is created.

Update shared comp UX

  1. Change the relevant kind/type contract or Studio component in FrameDiff.
  2. Test it against package fixtures and consumer examples.
  3. Projects receive it on their next dependency-pin update.

Upgrade a project

  1. Move its FrameDiff pin to a reviewed revision.
  2. Install, then run check and production build.
  3. Fix explicit current-contract errors; do not carry compatibility shims in the project.

Decision summary

Do not create new composition kinds for new engines, scaffolds, or workbenches. Add a runtime type only when package machinery genuinely differs; add a semantic kind only when creator intent and default authoring behavior genuinely differ; add a starter when an existing kind needs a convenient implementation recipe. Every new runtime type must define its versioned JSON data contract, factory validator, starter compatibility, package-owned Studio UX, registry-load test, curated example, and migration note. Keep version migrations centralized and dormant until a real backwards-compatibility requirement justifies them.
